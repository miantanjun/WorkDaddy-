# ck-memory 与主流记忆系统深度对比

> 日期：2026-11-04　被测对象：`scripts/ck-memory.js` / `ck-memory-ui.js` / `ck-mcp.js`（本机真实库 51039 条 / 1229 条有效记忆）
> 对比对象：Mem0、Zep/Graphiti、Letta(MemGPT)、Cognee、A-MEM、Generative Agents、MemoryBank、ChatGPT/Claude 原生记忆
> 方法：先读自家源码确认实现边界，再实测检索行为，最后对照各家论文与官方架构文档

---

## 一、先纠正一个前提

你的判断有一半对，另一半需要修正。

**对的那一半**：网上那些"厉害的记忆插件"确实不只是记录对话。它们会**用 LLM 把对话蒸馏成事实条目**（fact / memory block），再配上向量、图、时间戳，检索时按多种信号融合排序。Mem0 的原文说法是："By default, Mem0 stores extracted memories, not a verbatim transcript"——存的是"用户偏好靠窗座位"，不是原话"我喜欢靠窗的座位"。

**需要修正的那一半**：我们这套**也不完全是"把对话都记录下来"**。它做了三件超出"录音机"的事：

1. **噪声剥离**：宿主每轮注入的 40 多类固定块（system-reminder / memory_system / tool_use…）整段删掉，四类压缩摘要与续跑话术直接不入库。
2. **价值分层（pri）**：区分"你说的话 / 每回合我的结论 / 我的过程话与工具输出"，默认只检索前两档。这不是所有插件都有的——大多数向量方案反而最缺这个。
3. **重复折叠**：同一句话出现 962 次只存 1 行 + 计数。

所以更准确的说法是：**我们有"好的原始素材筛选"，但没有"从素材里提炼知识"这一步。** 差别在下面这张表里。

## 二、根本差异：一行表格说清

| | 我们（ck-memory） | 主流方案（Mem0/Zep/Cognee） |
|---|---|---|
| 存什么 | **原始对话行**（筛选后） | **提炼出的事实条目** |
| 一条记忆是 | "检索结果为什么没有排序"（用户原话） | "检索排序 bug 已修，根因是 bm25 未作主表" |
| 怎么找 | 关键词字面匹配（BM25） | 语义向量 + 关键词 + 实体 + 时间，四路融合 |
| 找"排序那事后来怎么修的" | **0 命中**（实测） | 命中"bm25 排序 bug 修复"条目 |
| 跨会话 | 不做（只有当前会话） | 默认跨会话、按 user_id 聚合 |
| 冲突处理 | 无（新旧两条都在，分不出谁对） | Mem0 的 ADD-only + 排序；Zep 的边失效 |
| 自动进上下文 | **不自动**，要我主动调工具 | 有自动注入路径 |

后两行是我们和它们最大的差异，下面单独说。

## 三、实测：我们这套现在到底能查到什么

不凭印象，直接打真实库。以下都是刚跑的结果。

### 3.1 ⚠️ 先说一个刚测出来的严重 bug（比"没有语义检索"更紧急）

**分层做了一半，把候选池淹了。**

实测：库里「压缩」这个词在有效记忆（pri>=1）里有 **33 条**，但 `search('压缩')` 返回 **0 条**。

根因不在分层本身，而在 `search()` 的 SQL 结构：

```js
// 现在的写法：内层只按 bm25 取 120 条，外层才过滤 sid/kind/pri
FROM (SELECT rowid AS rid, bm25(seg_fts) AS score
      FROM seg_fts WHERE seg_fts MATCH ? ORDER BY bm25(seg_fts) LIMIT ?) t
JOIN seg s ON s.id = t.rid
WHERE s.sid = ? AND s.kind IN ('user','assistant')
  AND COALESCE(s.noise,0) = 0 AND COALESCE(s.pri,0) >= 1
```

**问题**：`LIMIT 120` 取的是**全库** bm25 最高的 120 条。工具输出（pri=0）词频高、短语多，bm25 分数天然靠前，**这 120 个名额几乎全被工具输出占满**，等外层再筛 `pri>=1`，已经没剩几条了。等于分层把检索的口子收窄了，但候选池还是没分层时的样子。

实测对照（同一会话、同一批词）：

| 查询 | 旧写法（外层过滤） | 把过滤下推到内层 |
|---|---|---|
| 压缩 | **0 条** | **33 条** |
| 排序 | **0 条** | **16 条** |
| 面板 | 3 条 | 120 条 |
| 尾款 | 10 条 | 10 条 |

「面板」「尾款」碰巧工具输出里少，所以没暴露；「压缩」「排序」这种在过程话里高频出现的词，直接归零。

**修法**：把 `sid` / `kind` / `pri` 的过滤写进内层子查询，先过滤再取 top-N：

```sql
FROM (SELECT f.rowid AS rid, bm25(seg_fts) AS score
      FROM seg_fts f JOIN seg g ON g.id = f.rowid
      WHERE seg_fts MATCH ? AND g.sid = ?
        AND g.kind IN ('user','assistant')
        AND COALESCE(g.noise,0) = 0 AND COALESCE(g.pri,0) >= 1
      ORDER BY bm25(seg_fts) LIMIT ?) t
JOIN seg s ON s.id = t.rid
```

**这是当前第一优先级，比引入向量重要得多**——检索根本拿不到该拿的东西，谈别的都没意义。

### 3.2 同一个意思，换个说法就查不到

```
「尾款」                     → 命中 5 条  ✅
「尾款什么时候」             → 命中 0 条  ❌
「尾款什么时候能到」         → 命中 0 条  ❌
「面板」                     → 命中 3 条  ✅
「面板上怎么看记忆」         → 命中 0 条  ❌
「重启」                     → 命中 3 条  ✅
「改完要不要重启daemon」     → 命中 0 条  ❌
```

根因在 `toMatch()`：分词后把每个 2-gram 用 **AND** 连起来。

```js
return parts.map((p) => '"' + p + '"').join(' AND ');
```

「尾款什么时候」被切成 `尾款 款什 什么 么时 时候`，要求这 5 个 bigram **同一个文档里全部出现**。而「尾款」那几条记录里根本没有"什么时候"，于是全军覆没。

**这等于把"问得越具体，越搜不到"写进了设计里。** 而人问记忆时天然会说一整句。

我实测了 OR 的效果，但**不能简单改成 OR**：OR 会召回 39~52 条（库里 33 条含「压缩」的记录几乎全被带出来），全是噪声。需要配合**覆盖率重排**（按命中 bigram 比例排序）。但覆盖率也有坑——「什么时候」「多少钱」这类高频虚词会让覆盖率失效，必须配停用词表。这条路要走，但要比想象中细致。

### 3.3 单字必然查不到

```
「柜」 → 命中 0 条   （库里"五柜""柜号"等有 3 条）
```

因为入库时中文被切成 2-gram，单字「柜」压根不在索引词表里。而"柜"是外贸最核心的量词之一。

### 3.4 "只查当前会话"的真实代价

```
「231472」→ 0 条   （全库都没有这个数字）
「SHARDA」→ 0 条   （全库都没有）
「埃及」  → 0 条   （全库都没有）
```

⚠️ 这三条**是数据本来就没有，不是检索失败**。我一开始拿它们当测试用例，把自己误导了——查了才知道，`8f92c3fc`（当前会话）的内容几乎全是"开发记忆系统本身"的对话，埃及订单、波兰客户那些业务内容根本不在这个库里（在别的工作区/别的会话）。

**这件事本身说明了一个真实问题**：记忆按会话隔离，导致"我记得我跟你聊过埃及那单"和"记忆里真有"是两件事。等你换到别的工作区，之前积累的东西一条都带不过去。**这是"只查当前会话"设计的固有代价**——当时是你明确要求的（不想让别的会话内容串进来），但它也意味着**这套东西永远成不了"跨项目的长期记忆"**。

### 3.5 有效记忆的粒度是"整条消息"，没有切块

```
有效记忆 1229 条 | 平均 785 字 | 最长 12958 字 | 超 2000 字的 135 条
  0~100 字:  428 条
  300~1200 字: 178 条
  1200~2500 字: 369 条   ← 我的长篇总结
  2500+ 字:   37 条
```

一条 12000 字的总结被打成**一条**记忆。检索命中它时，返回的是一大坨文本，既占 token 又淹没重点。主流方案都会切成 200~500 字的 chunk，或提炼成一句事实。

### 3.6 检索延迟（1200 条有效记忆规模）

```
尾款   8 条  50.5ms
合同   1 条  31.6ms
其他   0 条  ~36ms
```

30~50ms，**这一点我们是赢的**——Mem0 一次检索要一次 embedding API 调用 + 向量查询，Zep 报 2.58s（GPT-4o 全流程）。本地 FTS5 是毫秒级的。

### 3.7 最根本的一条：记忆不会自动进入我的上下文

我在 `scripts/inject.js` 里搜过，**没有任何把记忆自动注入提示词的钩子**。`memory_search` 只在我主动调用时才发生。

后果很直接：**"我不记得的东西"和"我会想起来去查的东西"，是两个集合。** 真正被遗忘的东西，往往正是我想不起来要查的东西。这是当前架构最大的结构性缺口。

## 四、逐家拆原理，看差在哪一层

### 4.1 Mem0 —— "抽取 + ADD-only + 四路融合"

**写入六步**（官方 `docs.mem0.ai/core-concepts/memory-evaluation`）：

```
① 存原始对话
② 上下文查找（找相关旧记忆，避免重复）
③ LLM 单遍蒸馏 → ADD-only 的事实
④ 哈希去重 + 向量化
⑤ 实体链接（专名、引号内容、复合名词短语）→ 图
⑥ 时间推理（独立 pass：事件何时发生、是否持续、精度、类型）
```

**关键设计决策是 ADD-only**：新事实**不覆盖**旧事实，两条都留。冲突靠**检索时的时间/相关性排序**来体现新旧，而不是写入时删除。官方理由是"保留完整历史可审计"。

（早期版本用的是 ADD/UPDATE/DELETE/NOOP 四操作，2025 年论文里还是这套；2026 年的新算法改成了 ADD-only。）

**检索四路信号**：

| 信号 | 干什么 | 适合 |
|---|---|---|
| 语义向量 | 余弦相似度 | 概念性问题 |
| 关键词 BM25 | 词形还原后的词匹配 | 人名、ID、精确事实 |
| 实体 | 查询里的实体加权 | "Alice 怎么样" |
| 时间 | 写入时的时态元数据 vs 查询时态意图 | "什么时候…" |

四路**融合排名**（rank fusion），不是简单加权。

**公开成绩**：LoCoMo 92.5 / LongMemEval 94.4 / BEAM-1M 64.1 / BEAM-10M 48.6，平均每次检索 6956 token。

**我们对比**：六步里我们只做了 ①（存原始）和 ④ 的"哈希去重"（用 h + dup 折叠）。②③⑤⑥ **全没有**。检索我们是单路 BM25。

值得注意的是：**Mem0 也保留原始对话**（SQL 库存"history log"，ROLLING 消息窗口）。所以"存原文"不是罪，"只存原文"才是。

### 4.2 Zep / Graphiti —— "双时间知识图谱"

三层子图：
- **Episode 子图**：原始消息/JSON，无损真相源
- **Semantic 子图**：抽出的实体 + 关系边
- **Community 子图**：社区聚类 + 摘要节点（用于高层检索）

**核心创新是双时间（bi-temporal）**，每条边四个时间戳：

| 字段 | 含义 |
|---|---|
| `created_at` | 系统何时学到这条 |
| `valid_at` | 事件在现实中何时开始为真 |
| `invalid_at` | 何时不再为真 |
| `expired_at` | 系统何时得知它失效 |

**冲突处理逻辑**（这点非常值得抄）：新事实与旧边矛盾时，**不删旧边**，而是给旧边设 `invalid_at = 新边的 valid_at`，然后建新边。查询"当前为真"就过滤 `invalid_at = ∞`。

Zep 官方那篇《Stop Using RAG for Agent Memory》举的例子就是我们的日常：
> Day 1 说"我喜欢 Adidas" → Day 180 说"Adidas 鞋两个月就坏，我改买 Puma"
> 纯向量系统搜"我该买什么鞋"，最相似的是那条 Adidas，于是推荐 Adidas。

这个失败模式我们**一模一样会有**，而且我们没有时序，连"哪条更新"都判断不出来。

**成本**：Zep 的方式很吃 token（一次性 600k+ 的批评就来自这里），所以我们不能照抄它的"全量边维护"。但**"标失效而不是删"这个思想是零成本的**，只要加两列。

### 4.3 Letta / MemGPT —— "OS 分页 + 自编辑 + 睡眠整理"

三层：
- **Core memory**：常驻上下文的 memory block（`persona` / `human`），有 label、description、字符上限
- **Recall memory**：完整对话历史（关系库）
- **Archival memory**：向量库，按需检索

两个真正值得借鉴的工程判断：

**① 自编辑（self-editing）**：模型通过工具自己决定"这条该写进 core memory""这个 block 太长要压缩"。记忆管理是**模型的一种可推理行为**，不是外部管道的固定逻辑。

**② Sleeptime（睡眠时计算）**：主 Agent 空闲时，后台另起一个 Agent 扫描历史，做整理、去重、提炼、晋升与降级。而且**主 Agent 用快模型，sleeptime 用强模型**——因为后者不面向用户，可以慢。

> 这一条对我们特别有价值：我们的索引器每 30 秒跑一次，现在只做"原样搬运"。同样这个 30 秒的窗口，完全可以拿来做归纳。

**版本化**：记忆块改动留历史，能回溯"Agent 是在哪一步把画像改错的"。我们的 `seg` 表是原地更新，没有版本。

### 4.4 Cognee —— "ECL 管道 + memify 自我改进 + 14 种检索模式"

**ECL = Extract → Cognify → Load**，六阶段：

```
分类文档 → 查权限 → 提取 chunk → LLM 抽实体与关系
→ 生成多级摘要 → 嵌入并写图边
```

三库合一：**图库**（实体/关系/遍历）+ **向量库**（语义）+ **关系库**（chunk 与溯源）。默认全是嵌入式（SQLite + LanceDB + Ladybug），**零基础设施**——这点和我们用 `node:sqlite` 的思路一致。

**memify（最有借鉴价值）**：摄入后单独跑一轮，剪掉陈旧节点、强化高频连接、按使用信号重排边权重、补派生事实。**记忆不是静态存储，是会随使用进化的结构。**

**14 种检索模式**：从 `CHUNKS`（纯向量）到 `CHUNKS_LEXICAL`（BM25）到 `HYBRID_COMPLETION`（三者合一）到 `GRAPH_COMPLETION_COT`（图遍历 + 思维链）。核心洞察是**按查询类型路由**，而不是一招打天下——这正好命中我们"所有查询都用 AND-BM25"的病。

### 4.5 A-MEM —— "Zettelkasten 卡片 + 动态链接 + 记忆演化"

这是学术界我觉得最贴合"你说的那种记忆插件"的：

每条新记忆生成一张**结构化笔记**：
- 上下文描述（contextual description）
- 关键词（keywords）
- 标签（tags）
- 向量

然后**分析历史记忆库，找有意义的相似性，建立链接**。更进一步是**记忆演化**：新记忆进来时，会**回头更新旧记忆**的上下文描述与标签——整个网络的理解持续变精细。

**成绩**：LoCoMo 多跳任务比基线提升近 6 倍；token 只用 1200~2500，而 MemGPT 要 16900。

**这条最直接回答你的问题**：你说的"做成很多记忆块，再打上 tag，方便索引"——A-MEM 就是干这个的，而且已发 NeurIPS 2025。

### 4.6 Generative Agents —— 三因子检索公式（我们的衰减实现需要对照）

斯坦福小镇的经典公式：

```
score(m) = α · Recency(m) + β · Importance(m) + γ · Relevance(m)
```

| 因子 | 计算 | 注意 |
|---|---|---|
| Recency | `0.995 ^ 经过的小时数` | **时钟在"被检索"时重置，不是创建时** ⇒ 常用的记忆一直新鲜 |
| Importance | LLM 写入时打 1~10 分 | 结婚=10，散步=2 |
| Relevance | 查询与记忆的余弦相似度 | |

三因子都 min-max 归一化到 [0,1] 后求和（原论文权重全 1）。

**对照我们的 `agePenalty()`**：

```js
const DECAY_GRACE_DAYS = 7;      // 7 天内不罚
const DECAY_PER_DAY = 0.02;      // 之后每天 +0.02
const DECAY_CAP = 1.2;           // 封顶
```

差别有三个，都是实质性的：

1. **我们的时钟从"创建时间"算，不是"上次被用"算**。一条天天被查的关键结论，和一条从没被查过的碎话，衰减速度完全一样。**这是错的**——常用即重要。
2. **我们只有 recency，没有 importance**。pri 分层是粗粒度的 importance 代理（3 档），但没有细粒度打分。
3. **说法上更微妙**：`0.02/天` 且封顶 1.2 意味着 60 天就到顶，之后新旧无差。而 BM25 分值区间实测是 -8.48~-6.56，**1.2 的惩罚量级足以把结果整体重排**——这个权重是不是拍脑袋定的，值得复核。

### 4.7 MemoryBank —— 艾宾浩斯遗忘曲线

```
R = e^(-t/S)
```

`t` = 距上次访问的时间，`S` = 记忆强度（初始 1，**每被回忆起一次 +1，同时 t 归零**）。

这就是"常用即重要"的正式版本。配合分层摘要（日事件摘要 → 全局用户画像）。

**这印证了 4.6 的第 1 点**：业界共识是"回忆动作本身应该增强记忆"，我们完全没做。

### 4.8 ChatGPT / Claude 原生记忆 —— 两种极简路线

**ChatGPT**：两层——显式"保存的记忆"+ 隐式"引用聊天历史"。隐式那层靠后台巩固流程，内部代号 **Dreaming**，V3 在 2026 年 6 月上线，把事实召回从 67.9% 提到 82.8%。**注意"后台巩固"这个词——和我们前面说的 sleeptime 是同一件事。**

**Claude**：`/memories` 目录 + 文件读写工具。模型自己 create/read/update/delete 文件，跨会话持久。配套 **context editing**（自动清掉过期工具结果），官方说两者合用在一个 100 轮的搜索任务上带来 **39% 效果提升 + 84% token 节省**。

**Claude 这条路对我们最有参考价值**，因为它证明了：**不需要向量库、不需要图数据库，纯文件 + 模型自己整理，也能做到很好。** 门槛低、可审计、GDPR 友好。

| 写入：事实提炼 | **0** | 9 | **最大的洞**：一条事实都没提炼过 |
| 写入：去重折叠 | **6** | 8 | 有精确重复折叠，没有语义去重 |
| 表示：切块粒度 | **2** | 9 | 12000 字打成一条 |

| 检索：多信号融合 | **1** | 9 | 单路 BM25 + 一个时间惩罚 |
| 检索：延迟 | **9** | 6 | **我们赢**（30~50ms vs 秒级） |
| 检索：可解释性 | **9** | 6 | **我们赢**（能给出原文与前后文） |

| 上下文：自动注入 | **0** | 7 | **结构性缺口** |
| 工程：零依赖 | **9** | 5 | **我们赢**（node:sqlite 自带） |
| 工程：可删除可控 | **9** | 5 | **我们赢**（管理页 + 只删索引） |

按 CoALA 四分类（working / episodic / semantic / procedural）：

| 类型 | 我们现在 | 说明 |
|---|---|---|
| Working（工作记忆） | 客户端管 | 不归我们 |
| **Episodic（情景）** | **✅ 有** | 原始对话 = 情景记忆，这是我们的强项 |

| Procedural（程序） | ❌ 无 | 没有"这类任务该怎么做"的沉淀 |

**我们只做了三层里的一层。**

## 六、够不够好、成不成熟

**作为"当前会话的原文检索器"：够好，成熟。**
- 噪声过滤、分层、折叠、毫秒级、可解释、可删除、零依赖——这几项放在同类里都不落后，噪声过滤甚至是超配的。
- 1229 条有效记忆、30~50ms、全量回归 88 套件通过，工程上是扎实的。

**作为"记忆系统"：不够好，不成熟。** 有四个层次的问题，按严重度排：

**① 结构性：记忆不会自动进上下文（最严重）**
再好的检索，不被调用就等于没有。"我不记得"和"我想起来去查"是两个集合——这层缺口不补，其他优化都是在给一条断掉的管子加压。

**② 功能性：检索管道有两处硬伤**
- **候选池被噪声占满**：「压缩」明明有 33 条，返回 0 条。这是 SQL 结构问题，一行改动级别，但直接影响一半以上的查询。
- **AND 连接**：问得越具体越搜不到。

这两个都不是"能力不足"，是**实现缺陷**。修完之后，这套系统立刻会好用一大截。

**③ 表示层：只有原文，没有知识**
没有事实条目、没有 tag、没有实体、没有时序、没有冲突处理。你提到的"归纳整理成记忆块打 tag"，我们这块是 0。

**④ 生命周期：记忆不会变聪明**
没有"常用的记忆被强化"、没有"后台整理"、没有"新旧冲突时标失效"。记忆只是越堆越多。

一个直观的类比：**我们现在是一个很好的`grep`，还不是一个"记得住事的人"。**

## 七、该借鉴什么（按性价比排序）

原则：**能加在现有 SQLite 上的优先，要引入新基础设施的往后放。** 你的本地链路（`node:sqlite`、零依赖、单文件）是优点，不该为了追新把它丢掉。

### P0 — 一周内能做，收益最大

**1. 修候选池截断（最高优先级，一行改动）**
把 `sid` / `kind` / `pri` 过滤下推到内层子查询，先过滤再取 top-N。
实测「压缩」0 → 33 条，「排序」0 → 16 条。**这是目前性价比最高的一个改动。**

**2. 修 AND → OR + 覆盖率重排 + 停用词**
现在 `toMatch()` 用 AND，导致长查询必空。改成 OR 后**必须**配合覆盖率重排（按命中 bigram 比例），否则全是噪声；还要配中文停用词表（什么/时候/多少/我们…），否则虚词会让覆盖率失真。
预计「尾款什么时候」从 0 → 有结果。

**3. 单字兜底**
查询长度 < 2 且为 CJK 时，退回 `LIKE '%字%'` 或改用 unigram 索引列。修「柜」这类查询。

**4. 时间衰减的时钟改成"上次被检索"**
加一列 `last_hit_ts`，检索命中时更新它；`agePenalty` 用它而不是 `ts`。这是 Generative Agents 和 MemoryBank 的共同做法，**改动很小，语义正确性提升很大**。

**5. 重要度打分（粗版，零 LLM）**
先用规则代替 LLM：含金额/日期/单号/公司名/`决定`/`结论` 的加权，含"我先看一下""正在处理"的降权。等有 LLM 了再换成真打分。

### P1 — 一个月内，需要引入 LLM

**5. 事实抽取（这是你问的核心）**
索引器每 30 秒那一轮，本来就在读新消息。让它顺带做一件事：**把新入的 1~2 个回合送给 LLM，抽出结构化事实**。

建议 schema（借鉴 Mem0 + A-MEM，但保持极简）：

```sql
CREATE TABLE fact (
  id INTEGER PRIMARY KEY,
  sid TEXT,              -- 来源会话（保留溯源）
  src_seg_id INTEGER,    -- 来自哪条原文，可回查
  text TEXT,             -- 一句事实："OCTAGON 尾款 USD 231,472.08 未付"
  tags TEXT,             -- JSON 数组：["订单YKW-SU-260713","付款","埃及"]
  entities TEXT,         -- JSON：{"客户":"OCTAGON","金额":"231472.08","币种":"USD"}
  valid_from INTEGER,    -- 何时开始为真
  valid_to INTEGER,      -- 何时失效（NULL = 现在仍有效）
  importance INTEGER,    -- 1-10
  hits INTEGER DEFAULT 0,-- 被检索次数（用于强化）
  created_at INTEGER
);
```

**关键：`valid_to` 而不是删除。** 这是 Zep 的核心思想，成本只是多一列，但直接解决了"Adidas vs Puma"那类问题。

**抽取提示词要按你的业务定制**——这是通用插件做不到、而我们能做的最大优势：

> 你是外贸单证助手。从下面这段对话中抽取"以后还会用到的事实"，只抽这些类型：订单号与条款、金额与币种、付款状态、船期与港口、单据编号、客户与联系人及其偏好、地址与税号、做过的决定与理由。**不要抽**过程描述、寒暄、工具命令。每条事实一句话、自包含、带时间。输出 JSON 数组。

**6. 切块**
长消息按语义边界（标题/空行/句号）切成 ≤500 字。现在 12000 字一条的问题直接解决。

**7. 混合检索**
词面（FTS5）+ 语义（向量）双路，用 RRF（Reciprocal Rank Fusion）融合。语义那路可以很轻：本地 `qwen3.8-27b` 当前不可用（8090/8091/8094 都探不通），但网关里有 DeepSeek，embedding 可以走网关；退一步也可以只做"LLM 重排"（拿 FTS 前 40 条让 LLM 排序），成本更低、效果立竿见影。

### P2 — 需要更大改造

**8. 自动注入（补结构性缺口）**
两条路，建议都做：

- **被动**：客户端一启动/切换会话，就把"当前会话的有效事实摘要"（≤800 字）注入上下文。可以走 `inject.js` 已有的钩子位，或者写进会话开头的 system 注入。
- **主动**：在工具描述里写清楚"**回答任何涉及历史细节的问题前，先调 memory_search**"，并把这条写进用户级 `MEMORY.md`，让我每次都看到。

**9. 后台巩固（sleeptime）**
借用 Letta 的思路：空闲时跑一轮，把零散事实合并、把矛盾的标失效、把长期没用的降权。**用我们本地/网关的模型，不占用你等结果的时间。**

**10. 记忆质量评测**
现在有 148 条单测，但全是"功能是否工作"，没有一条是"记得对不对"。建议照 LoCoMo 的分类自建一个小评测集。

⚠️ 用**本会话真实存在的内容**做用例（我刚开始拿"埃及订单"当例子，结果全库都没有这个词，白测了一轮）：

| 类别 | 例子（基于真实库内容） | 现在能不能过 |
|---|---|---|
| 单跳 | "尾款" | ✅ 10 条 |
| 候选池 | "压缩" | ❌ **0 条**（库里 33 条） |
| 换说法（长句） | "面板上怎么看记忆" | ❌ 0 条（"面板"单独 3 条） |
| 多跳 | "索引翻倍和重复折叠是不是一回事" | ❌ |
| 时序 | "排序那个 bug 是先发现还是后发现的" | ❌ |
| 知识更新 | "删除功能后来是不是又加了日志" | ❌ |

## 八、三条不建议抄的

保持克制，别被带跑：

**1. 不要上完整知识图谱（Neo4j 那套）**
Zep/Cognee 的图很有用，但它们的场景是"多用户、多租户、企业级"。你是一个人用、几十条会话，图的复杂度收益远小于维护成本。用 SQLite 的 `fact` 表 + `entities` JSON 列 + `LIKE`/FTS 就够覆盖 90% 的查询。

**2. 不要照抄 Mem0 的"每次写入都调一次 LLM"**
Mem0 每次 add 都要 1 次蒸馏 + 1 次时间推理。你是 30 秒一轮的持续索引，这么干 token 成本会失控。**改成批量：攒够 5~10 个回合或 10 分钟再抽一次。**

**3. 不要为了"先进"牺牲零依赖**
`node:sqlite` 自带、单文件、可删可卸，这是 WorkDaddy 整个项目的优点。向量库可以后加（甚至可以只用网关 API 不落地），但**主存储必须是 SQLite**。

## 九、结论

**你的直觉是对的：主流方案确实在做"归纳成记忆块 + 打 tag + 按需索引"，而我们没做。** 这不是"差不多"，是**少了一整个层次**——我们只有情景记忆（原文），没有语义记忆（事实）。

**但也不必全盘否定我们做的：** 噪声过滤、价值分层、重复折叠、毫秒级、可解释、可删除——这几项我们做得不差，其中"价值分层"和"噪声过滤"甚至是多数开源方案缺的（它们直接吃聊天记录，不知道宿主注入是什么）。

**最该先动手的不是"上向量"，而是这三件低成本的事：**
1. **修候选池截断**（过滤下推，一行改动）——「压缩」从 0 条变 33 条，这是实测最触目的一个
2. 把 AND 改成 OR + 覆盖率重排 + 停用词（直接决定"长句能不能查到"）
3. 让记忆能自动进上下文（不然前面全白做）

**然后才是"事实抽取"这个大工程**——但正是它，才把"记录"变成"记忆"。

一句话总结：**我们现在是一条很扎实的"记忆索引"，但离"记忆系统"还差提炼、时序、巩固、注入这四步。** 而缺的这四步，恰好就是你说的那些"厉害插件"在做的事。

**另外要坦白一件事**：我在做这次对比时先测了一堆"客户欠我多少钱"之类的查询，结果全是 0，一度以为只是"没有语义检索"的局限。**查到根因才发现其中一半是我自己的 SQL 写错了**——候选池被工具输出占满，分层形同虚设。所以这次对比最大的收获可能不是"该抄哪家"，而是**把两个实打实的 bug 挖出来了**。

## 十、六个阶段施工后的复盘（2026-11-04）

上面 3.1–3.7 那些实测结论都还成立，但它们是**施工前**的状态。这一节记录做完之后的变化，
以及**哪些判断被证明是错的**。

### 10.1 客观基线（第一次有尺子）

评测集在 `.wd-analysis/eval/`：39 条用例全部取自本机真实会话，
按 LoCoMo 分 `single 16 / multi 5 / temporal 5 / open 5 / negative 8`，金标准用 `seq` 而非 `id`。

| 路 | 严格 Recall@k | 回合级 | MRR | 负例拒答 |
|---|---|---|---|---|
| `seg`（原文 bigram） | 41.9% | 48.4% | 0.500 | 75.0% |
| `fact`（事实词法） | 19.4% | 25.8% | 0.022 | 87.5% |
| `ent`（实体精确） | 0.0% | 0.0% | 0.000 | 100% |
| **`fuse`（三路 RRF）** | **54.8%** | **61.3%** | 0.248 | **75.0%** |

三点值得记下来：

- **融合比单路原文高 12.9 个百分点，且拒答率不下降。** 这是阶段 5 的融合设计第一次被量化
  证明有效 —— 在此之前只有「查 LB48-B 时 `lanes=2`」这种个案证据。
- **`ent` 单路 0% 完全正常。** 实体路只认精确等值，而评测题大多不是「报个单号」。
  它的价值体现在融合路的 `lanes=2/3`，不在于单路能答多少。**看单路排名会误判它的作用。**
- **事实层单路 MRR 只有 0.022。** 这是个真实短板：事实是提炼过的短句，和原问题的用词
  距离比原文更远，词法路吃亏。它真正的价值在换说法命中（`open` 类），而那类题在评测集里只占 5 条。

### 10.2 负例拒答 0% → 75%，以及四条走不通的路

修之前 8 条负例 **100% 被答了出来**。命中的全是 `怎么`(df 437) / `阈值`(df 83) / `的`(df 1897)
这类通用词 —— OR 兜底只要有词能命中就一定返回东西。

唯一有效的判据性质是**确定性字面**：

- `latinMiss`：罕用英文专名**整词整库查无** ⇒ 这个话题一定没讨论过
- `idMiss`：`strongIds` 给出的标识符整库字面查无 ⇒ 同上

拦得住 N01/N02/N04/N05/N06/N08，拦不住 N03（Redis 集群 slots）与 N07（Server Actions 缓存策略）
—— 这两个如实记为已知边界。

**四条被实测否定的路，别再重试：**

1. **IDF 加权覆盖率做阈值 —— 方向是反的。** 负例 N07 覆盖率 72.9%，
   比 31 条正例里 29 条都高。中文短句的覆盖率主要由常用词贡献，跟「话题是否讨论过」无关。
2. **未登录词率。** 12% 阈值能拒 88% 负例，但要砍掉 42% 正例。问法本来就自由，缺词是常态。
3. **「内容词一个都没打中」。** N07 的 `服务/缓存/策略` 在库里比比皆是，命中率 6/6 = 100%。
4. **纯词法判断语义相关性。** 与阶段 2 的结论完全一致：中文 bigram 判断不了这件事。

### 10.3 被推翻的三个原有判断

这次施工推翻了我自己写在这份文档里的三条判断，都记下来：

| 原判断（本文件 3.x 节） | 实际 | 为什么错 |
|---|---|---|
| 「候选池截断要**把过滤条件下推**到内层子查询」 | **不能下推**。正解是内层 `LIMIT pool` 改 `LIMIT -1` | 下推会废掉 FTS 的 top-N 优化，实测 300ms；不设限反而只 11ms |
| 「AND 改 OR + 覆盖率重排」 | **不能默认改 OR**。正解是 AND 优先 → 0 条才 OR 回退 | 直接 OR 会召回 39~52 条噪声，比漏召回更坏 |
| 「加中文停用词表」 | **不能硬编码词表**。用 `fts5vocab` 的 df 让数据决定 | 实测停用词表把有效词也筛掉了，效果更差 |

共同点：三条都是「听起来合理、动手就翻车」。这也是为什么要先建评测集再改代码。

### 10.4 与主流方案差距的更新

原结论「离记忆系统还差提炼、时序、巩固、注入这四步」——

- ✅ **提炼**（阶段 4）：`fact` 表 + LLM 抽取 + ADD-only + 双时间
- ✅ **注入**（阶段 2）：`UserPromptSubmit` hook，只认强标识符 + 稀有度
- ✅ **时序**（阶段 3~4）：`valid_from`/`valid_to` 双时间，旧的「未付」仍然查得到
- ⏳ **巩固**（本题的下一步）：sleeptime 后台整理 —— 去冗余、合并同义、补实体链接、修正误判失效

**仍然缺的两块**（不是这一轮能补的）：

- **向量路**：换说法但用词完全不重叠时，词法 + 实体都是盲的。这是 Mem0 四路信号里我们没有的那一路。
- **自编辑/演化**：Letta 的 `sleeptime` agent 能改写自己的记忆块，A-MEM 的卡片会互相链接演化。
  我们的 `fact` 目前只增不改，`valid_to` 是唯一的变化方式。

### 10.5 一句话

**评测集比任何一次改动都值钱。** 前五个阶段全靠「按设计推理 + 个案抽查」，而抽查挑的都是
改的时候心里惦记的那个词 —— 天然偏向新实现。有了 39 条固定题 + 固定判据之后，
才第一次能回答「这次改动到底是变好还是变坏」，也才敢动 `search()` 的主链路。

## 十一、阶段 6 后半段：sleeptime 后台整理（2026-11-04）

### 11.1 做了什么

抽取（`factTick`）是**加法**，只往库里塞、从不回头。时间一长必然留下三种垃圾：
同一件事被抽成多条表述、有些事实的实体没进 `ent` 表、被冲突规则误标失效。
整理就是趁没人用的时候清这些。

| 动作 | 默认 | 风险 | 说明 |
|---|---|---|---|
| **补实体链接** | ✅ 开 | **无判断** | 纯本地重算同一份文本，算错也只影响「能被哪个键搜到」 |
| **合并同义** | ❌ 关 | 高 | 见 11.2 —— 实测判据做不到既不误合又合得动 |
| **恢复误标失效** | ❌ 关 | 中 | 只认 `vt_reason='conflict'`，`manual` 一条不碰 |

三条硬约束落在代码里：**不删行**（只标 `valid_to`）、**可回滚**（`consol_log` 存前后快照）、
**有日志**（一次整理一个 `run_id`，整批可查可退）。

### 11.2 核心结论：自动合并不可行，改成「人定」

这是这一阶段最重要的一条负结论，值得单独记。

**实测数据**（8 组人工构造的同义表述，每组 3 种说法）：

| | 词面 jaccard |
|---|---|
| 同义组内（应合并） | 最低 **0.409** / 中位 0.625 / 最高 0.818 |
| 「已装运 / 未装运」（**必须拒绝**） | **0.733** |
| 「AB-260713 / CD-260713」（**必须拒绝**） | **0.750** |

⇒ **同义组的最低值比对照组还低。** 任何单一阈值都不可能「既合得动同义、又不合掉相反的意思」。
想让 0.409 那对合掉，阈值必须 ≤0.40；而 ≤0.40 在真实库里会把大量「同主题不同结论」的事实误合。

三道硬判据（数值集合相等 / 实体不交即跳过 / 状态词不对立）能把对照组**全部**挡住 ——
所以问题不在判据不够，而在**语义相似度本身没有可用的阈值**。

**误合与漏合是不对称的**：

- 误合 ⇒ 那条结论从检索里消失，**用户不知道自己被丢了什么**。
- 漏合 ⇒ 检索结果里多几条相似的话，一眼能看见，用户自己决定。

⇒ 设计改成：程序负责**找候选 + 列正面理由 + 列一票否决项**，
人点确认才改，改错随时回滚。面板上把「为什么没有一键自动合并」直接写出来，
否则用户只会觉得功能没做完。

这就是与 Mem0 的分歧点：Mem0 敢全自动，是因为它有条短条目 + 向量路；
我们只有词法 + 实体，装不起这个门面。

### 11.3 顺带补的一个真缺陷：失效原因不可区分

`valid_to` 有值这件事，在此之前**无法区分**是「冲突自动标的」还是「用户在面板上手动标的」。
而这两者对整理的意义完全相反：自动标错该恢复，手动标**绝不能碰**。

修法 = 新增 `vt_reason` 列（`conflict` / `manual` / `merge`），三处写入点各自标记。
**历史行不回填** —— 失效原因已无从考证，填一个猜的值比留 NULL 更坏
（NULL 的语义是「不知道 ⇒ 别碰」，这恰好是正确的）。

### 11.4 整理前后对比（合成数据，`eval/run-consol-eval.js`）

真实库只有 24 条事实、几乎无冗余 ⇒ 在它上面跑整理改动是 0，前后对比必然「逐位一致」，
什么都证明不了。所以这份评测在临时副本库上造 32 条事实（8 件事 × 3 种表述 + 4 对陷阱）来跑。

| | Recall@5 | 结果里的重复率 |
|---|---|---|
| 整理前 | 100.0% | **57.9%** |
| 整理后 | 100.0% | **0.0%** |

- 同义组识别 **8/8**（全部进了候选且无否决项）
- 对照组误判 **0/4**（2 对带否决项被明确标注，1 对未达阈值未进候选，1 对因数值不同被拒）
- 回滚 **完整还原**（28 条日志逐条退回，有效事实回到 32 条）
- **召回不降** —— 这是整理有没有把有用的东西合掉的硬指标

### 11.5 四组反向验证

断言全绿不算数，得能证明「判据错了会红」：

| 故意破坏 | 结果 |
|---|---|
| 合并判据的实体条件方向写反 | 5 条断言红（真同义反而不合、AB/CD 被合） |
| 合并改成 `DELETE FROM fact`（删行） | 5 条断言红（`__MISSING__` 直接暴露「行没了」） |
| 去掉「后继仍活着则不恢复」这道闸 | 1 条红（演变链成立时被强行翻案） |
| 恢复时把 `manual` 也纳入 | 1 条红（人的判断被机器覆盖） |
| 回滚改成正序 | 1 条红（同一事实改两次后停在中间态） |

最后一条最初**没测出来** —— 因为测试数据里每条事实只被改过一次，正序倒序结果一样。
补了「手工写两条日志构造同一条 fact 被改两次」的用例之后才抓得住。
这类「断言看起来在测、其实测不到」的情况，只有靠反向验证才暴露。

### 11.6 与主流方案差距的最终更新

第 10.4 节里列为 ⏳ 的**巩固**，现已落地（补实体自动、合并/恢复人定）。

仍缺的两块没变，而且现在知道得更具体了：

- **向量路**：11.2 那组数据就是它缺席的代价。~~有向量的话，「已装运 / 未装运」
  的语义距离会明显大于「同一件事的两种说法」~~ —— **这句预测已被实测推翻，见第十二节。**
- **自编辑/演化**：仍然只增不改，`valid_to` 是唯一的变化方式。
  整理这次动的是「状态」，不是「内容」—— 事实正文一个字都没被改写。

## 十二、阶段 7 前置侦查：向量路到底值不值得做（2026-11-04）

这一节**不是施工记录，是判决书**。上一节 11.6 我写过一句话：

> 「有向量的话，『已装运 / 未装运』的语义距离会明显大于『同一件事的两种说法』」

写的时候当成常识，没测。真正动手前先测了，结论是**这句是错的**。
记在这里，因为它同时推翻了一个技术判断和一个更根本的假设。

### 12.1 实验条件

本地服务当前离线（8094 / 8091 都 502），网关 20 个模型全是 chat、无 `embeddings` 端点（404），
所以只能用**本地 ONNX 跑**。模型 `BAAI/bge-small-zh-v1.5`（512 维，中文专用，24MB int8 / 94MB fp32），
`onnxruntime` + `tokenizers` 直接跑，不走 fastembed（它写死走 GCS 下 tar.gz，本机不通）。

语料沿用阶段 6 那组的 8 组同义表述（**口径一致才能和 jaccard 数字对比**），
对照组扩到 12 对，全部是本项目真实出现过的「看起来像、其实不能合」的组合。

### 12.2 结论一：向量分不开「同义」和「相反」

| 模型 | min(同义) | max(对立) | 间隙 |
|---|---|---|---|
| bge-small-zh int8 | 0.9291 | **1.0000** | **−0.0709** |
| bge-small-zh fp32 | 0.9350 | **1.0000** | **−0.0650** |

扩到 12 对后更清楚：

```
同义(应合) n=12  min=0.7705  med=0.9426  max=0.9839
对立(禁合) n=12  min=0.6830  med=0.9159  max=0.9473
⇒ 间隙 = 0.7705 − 0.9473 = −0.1768；12 组同义里有 7 组被压在对立组最大值之下
```

**这比词面的结论更糟**：词面是「同义最低 0.409 < 对照 0.733」（差 0.32），
向量是「同义最低 0.77 < 对立最高 0.95」（差 0.18）。两者**同命**：
「已装运 / 未装运」只差一个字，在向量空间里几乎是同一个点（0.948）；
而「记忆库文件在 APPDATA 下的目录里」vs「记忆库文件放在 APPDATA 下的目录」这种
实打实的同义（0.9883）也没比它高多少。

⇒ **向量不是「语义相反」的探测器**。它擅长「换了整套说法的同一概念」，
不擅长「只差一个否定词的同一句话」，而后者恰恰是合并判定最危险的情形。

### 12.3 结论二：英文编号在中文词表里直接消失（比词面更危险）

这一条是意外发现，也是**最该记住的一条**：

```
'订单 AB-260713 尾款 USD 100 已付'
tokens: ['[CLS]','订','单','[UNK]','-','260','##71','##3','尾','款','[UNK]','100','已','付','[SEP]']
'订单 CD-260713 尾款 USD 100 已付'
tokens: ['[CLS]','订','单','[UNK]','-','260','##71','##3','尾','款','[UNK]','100','已','付','[SEP]']
```

`AB` / `CD` / `XY` **全部映射成 `[UNK]`**，两条文本的 token 序列**逐位相同** ⇒ 余弦相似度
**精确等于 1.0000**。实测扰动矩阵（fp32）：

| | AB-260713 | CD-260713 | AB-260714 | XY-260713 |
|---|---|---|---|---|
| AB-260713 | 1.0000 | **1.0000** | 0.9897 | **1.0000** |
| CD-260713 | 1.0000 | 1.0000 | 0.9897 | 1.0000 |
| XY-260713 | 1.0000 | 1.0000 | 0.9897 | 1.0000 |

对比词面 jaccard 是 **0.750**（还能勉强区分）。所以在这个场景里，
**向量比词面更差**，而且是「看起来最像、最容易误合」的那种差。

⚠️ 这条对**检索**同样致命：项目里到处是 `YKW-SU-260713` / `7863` / `v1.9.9` 这类编号，
而向量对它们的区分能力接近零 —— 唯一的救法是**实体路单独兜底**（阶段 5 已有）。
换言之：向量路即便加，也**绝不能替代**实体路，只能是锦上添花的一路。

### 12.4 结论三：真正的瓶颈不是召回，是排序

这是本轮**最有价值**的一条，而且它把整个「向量路」的设计前提推翻了。

先看候选池的真实覆盖（默认路径 pri>=1，31 道正例）：

| 状况 | 题数 | 占比 |
|---|---|---|
| gold 排进前 5 | 19 | 61.3% |
| gold 在池内但排 6-20 | 8 | 25.8% |
| gold 在池内但排 21-50 | 1 | 3.2% |
| gold 在池内但排 51+（最高 112） | 1 | 3.2% |
| **gold 压根不在候选池** | **2** | **6.5%** |

候选池平均 **189 条**（最多 351），gold 有 **29/31 = 93.5%** 都在池里。
⇒ **召回几乎不是瓶颈，排序才是。**

这个判断直接决定了向量该怎么用：候选池里本来就有答案，
再加一路「向量召回」只是把同样的东西再捞一遍 —— 应该做的是**在池内重排**。

### 12.5 逐层拆解：产品排序里有一层在伤召回

OR 路径的排序是三段式，分开量结果如下（31 题 Recall@5）：

| 排序方式 | Recall@5 | 说明 |
|---|---|---|
| ① 裸 bm25 序 | **48.4%** | |
| ①+② 覆盖率定名次（不换位） | 48.4% | 覆盖率作为主键**不伤**召回 |
| ①+② 覆盖率 + **新鲜度换位**（= 产品现状） | **41.9%** | ⚠️ **掉了 2 题 / 6.5pp** |
| ①+②+③ 再多样性过滤 | 48.4% | 多样性过滤**零损耗** |

⇒ **伤召回的是阶段 3 加的「并列组内新鲜度换位」，不是覆盖率、不是多样性过滤。**
（下一小节的参数扫描显示实际损害到 **−9.7pp**，比这张表更严重 ——
这张表用的是产品真实输出，受产品其它层影响，是保守估计。）

**参数扫描**（`RANK_TIE` 是「名次差多少以内算并列」的阈值）：

| 设置 | Recall@5 | 前5平均新鲜度 | 被换进来的比例 |
|---|---|---|---|
| 不换位（关） | **48.4%** | 0.995 | 3.2% |
| RANK_TIE = 1 | 38.7% | 0.998 | 20.6% |
| RANK_TIE = 2（现状） | **38.7%** | 0.998 | 25.2% |
| RANK_TIE = 3 | 38.7% | 0.998 | 20.6% |
| RANK_TIE = 5 | 38.7% | 0.998 | 27.7% |

⚠️ 这张表的数字**改过一次**，过程值得记：
第一版把 `importanceOf` 的「含强标识符 +0.20」「长度 40~400 字 +0.10」两项漏了
（前者还用错了索引：拿 `seq` 去查按 `id` 建的表），算出的是 45.2%。
补齐后是 **38.7%** —— 也就是说换位的实际损害是 **−9.7pp**，比第一版显示的更严重。
**指标口径抄错不会报错，只会给你一个方向对、幅度错的数字。**

这张表给出了**比「掉 2 题」更硬的结论**：

1. **召回损失对阈值完全不敏感** —— 1/2/3/5 全是 38.7%。说明这不是「阈值没调好」，
   而是换位机制本身在动不该动的行（每次换掉 20~28% 的结果）。
2. **换位几乎没带来新鲜度收益** —— 0.995 → 0.998，差 0.003。
   注意这一列是**真实计算**的（`ts` 确实取到了），0.995 这么高是因为评测库里
   绝大多数 seg 都是近期的，30 天半衰期下新鲜度本来就接近 1 ⇒
   **在这份数据上，「偏好新内容」这件事根本没有发挥空间**。

⚠️ 但**仍不能直接删掉这一层**，两个理由：

- 31 题样本，差距虽大（p 需要重算）但仍是小样本；
- 它要解决的问题（「同一结论说了好几遍，应取最新的那条」）在评测集里**根本没有对应题目**，
  所以才看不出收益 —— 这是**评测集的盲区**，不是它没价值。

⇒ 正确的下一步：**先给评测集加「同一事实有新旧两个版本」的题**，
把新鲜度收益量出来；在那之前不动产品代码。

⇒ 正确的下一步：**先给评测集加「同一事实有新旧两个版本」的题**，
把新鲜度收益量出来；在那之前不动产品代码。

⚠️ 附一条方法论教训：我第一版给「新鲜度」算分时，用的字段在导出的 rows 里根本不存在，
导致那一列全是 0（0.995/0.998 是标签值不是真实计算值）。**指标算错不会报错，
只会给你一个看着合理的数字。** 任何指标第一次出现都必须先打印原始分布核对。

### 12.6 向量做成「池内重排」的效果，以及为什么仍然不下结论

沿用上一节口径，只换排序、不动召回：

| 方案 | Recall@5 | vs 产品 |
|---|---|---|
| 产品现状 | 41.9% | — |
| 裸 bm25 | 48.4% | +6.5pp |
| 向量单独排序 | 41.9% | +0.0pp |
| RRF(覆盖率序, 向量) k=60 | 58.1% | +16.1pp |
| RRF(裸 bm25, 向量) k=60 | 61.3% | +19.4pp |
| RRF(裸 bm25, 向量) k=10 | **64.5%** | **+22.6pp** |
| RRF + 多样性过滤 | 64.5% | +22.6pp（过滤零损耗） |

看上去很好，但**三项检验都要求我谨慎**：

1. **净贡献已被排除混淆**：向量在「裸 bm25」之上的独立贡献是 **+16.1pp**（48.4 → 64.5），
   不是全靠换排序口径。这一条是成立的。
2. **显著性不足**：McNemar 精确检验 → `base错→rrf对 10`，`base对→rrf错 3`，**p = 0.0923**。
   31 题样本下这**不显著**，按项目惯例不能当成结论。
3. **有一组反例**：用「覆盖率序」做融合时只有 58.1%，加入多样性过滤后反而掉到 **38.7%**
   （见 `probe-orderlayers.json`）。融合的排序基座是什么，结果差很多 ——
   这说明 +22.6pp 里有相当一部分来自「排序基座换了」，而不是融合本身。

⇒ **判决：向量路「有信号、但证据不足以支撑工程化」。**
下一步不是上手写向量栈，而是**先把评测集扩到 100+ 题**，
把 p 值做进显著区间，再决定要不要为它引入 ONNX 运行时、模型文件（24MB）、
增量编码队列这一整套设施。

### 12.7 顺带纠正两处我自己的判断

- 12.5 那 6.5pp 是**零成本**就能拿的（不需要任何新依赖），
  但它牵涉阶段 3 的核心设计，必须单独做实验，不能顺手改。
- 12.3 的编号 `[UNK]` 问题决定了：**即便将来加向量，实体路也绝不能撤**。
  这条要写死在设计里，不能靠「记得」。

### 12.8 判决与下一步

**向量路：有信号，但证据不足以支撑工程化。这一轮不动产品代码。**

判它的三条依据：

| 检验 | 结果 | 含义 |
|---|---|---|
| 净贡献（排除排序口径混淆） | +16.1pp | 信号是真的 |
| McNemar 精确检验 | **p = 0.0923** | 31 题样本下**不显著** |
| 换排序基座后 | 58.1% ~ 38.7% | 波动极大，说明「涨幅」有相当部分来自基座而非融合 |

按项目一贯规矩（阶段 2 那四条失败路线、阶段 6 自动合并），
**不显著的信号不做工程化** —— 那会引入一整套 ONNX 运行时 + 24MB 模型 +
增量编码队列，最后可能只是买到一个噪声。

**真正该做的下一步，按价值排序：**

1. **把评测集从 39 题扩到 100+ 题**（前置条件，不做这个后面全是空谈）
   - 当前 31 道正例算不出显著性，这是所有结论的共同瓶颈；
   - 需要补的题型：同一事实的新旧版本（量新鲜度收益）、跨会话指代、
     长文档内定位（现在 seg 中位数 387 字，天然偏短）。

2. **修 12.5 那个 6.5~9.7pp**（零成本，但要先有题）
   - 先加「新旧版本」题，把换位的新鲜度收益量出来；
   - 若收益确实可忽略 ⇒ 缩窄作用域或关掉；若收益真实 ⇒ 保留并接受召回损失，
     但要写清这是**有意为之的取舍**。
   - ⚠️ 这是当前**最值钱的一项**：不需要任何新依赖、不引入新组件，
     纯粹是「有一个开关一直开着但没量过」。

3. **向量路**（等 1、2 完成后再评估）
   - 若届时 p 值进显著区间，再考虑落地；
   - 落地时的硬约束：**必须是「池内重排」而不是「第四路召回」**（12.4 已证明召回不是瓶颈），
     且**不能替代实体路**（12.3 已证明向量对编号失明）。

**一句话**：这轮没有生产一行产品代码，但把一个原本要花几天的方向否掉了，
并且顺手找到了一个真实存在、零成本的 6.5pp —— 这比硬着头皮上向量路值。
